# Company IAM + microservices authentication starter

This is a runnable starter architecture for an IAM identity provider and three resource APIs:

- `Company.IAM.Api`: ASP.NET Core Identity + OpenIddict authorization server.
- `Company.Security`: shared standard `JwtBearerDefaults.AuthenticationScheme` validation and scope policies.
- `Company.Billing.Api`: accepts user tokens (`billing.read`) and calls Pricing with its own Client Credentials token (`pricing.read`).
- `Company.Pricing.Api`: validates `pricing-api` audience and `pricing.read` scope.
- `Company.Payment.Api`: accepts user tokens (`payment.read`) and calls IAM user profile API with its own Client Credentials token (`users.read`).

## Runtime note

The solution targets .NET 10 LTS. .NET 9 reached end of support on November 10, 2026. To retarget for a legacy environment, change all `net10.0` TFMs to `net9.0` and align package versions, but do not deploy an unsupported runtime in production.

## 1. Prerequisites

- .NET 10 SDK
- Docker Desktop
- EF Core CLI: `dotnet tool install --global dotnet-ef --version 10.0.15`
- HTTPS development certificates trusted: `dotnet dev-certs https --trust`

## 2. Start SQL Server

From the repository root:

```bash
docker compose up -d sqlserver
```

The included password is for local development only. Change it before use outside a disposable local environment.

## 3. Configure local secrets

Set environment variables (PowerShell example):

```powershell
$env:Clients__Billing__Secret = "billing-local-secret-change-me"
$env:Clients__Payment__Secret = "payment-local-secret-change-me"
$env:ServiceAuth__ClientSecret = "billing-local-secret-change-me" # Billing API
$env:BootstrapAdmin__Email = "admin@example.test"
$env:BootstrapAdmin__Password = "Use-A-Strong-Local-Only-Password!"
```

For Payment API, run with its own environment:

```powershell
$env:ServiceAuth__ClientSecret = "payment-local-secret-change-me"
```

Never commit client secrets, bootstrap passwords, PFX files, or production connection strings. In production use a secret manager and separate secrets per environment.

## 4. Create IAM database schema

From the repository root:

```bash
dotnet tool restore
dotnet ef migrations add InitialIamSchema --project src/Company.IAM.Api --startup-project src/Company.IAM.Api
dotnet ef database update --project src/Company.IAM.Api --startup-project src/Company.IAM.Api
```

The first command is optional if `dotnet-ef` is already installed globally. The database migration is deliberately a deployment step; do not run migrations automatically on every replica at startup.

## 5. Run the services

Use separate terminals:

```bash
dotnet run --project src/Company.IAM.Api --urls https://localhost:7001
```

```bash
dotnet run --project src/Company.Pricing.Api --urls https://localhost:7003
```

```bash
# Billing service: set ServiceAuth__ClientSecret to the billing-service secret
dotnet run --project src/Company.Billing.Api --urls https://localhost:7002
```

```bash
# Payment service: set ServiceAuth__ClientSecret to the payment-service secret
dotnet run --project src/Company.Payment.Api --urls https://localhost:7004
```

IAM seeding creates OAuth scopes/resources, the Angular public client, the Billing and Payment confidential clients, and an optional bootstrap user. It expects the EF migration to have been applied first.

## 6. Verify OIDC discovery and JWKS

Open:

- `https://localhost:7001/.well-known/openid-configuration`
- Follow the returned `jwks_uri` to inspect public signing keys.

Do not hardcode the JWKS path. Use the `jwks_uri` returned by discovery. The metadata document is generated by OpenIddict from the configured issuer, endpoints, grants, scopes and signing credentials.

## 7. User login from Angular

The Angular client is a public OAuth client with no client secret. Use a maintained OIDC client library and Authorization Code + PKCE (`S256`). Configure:

- authority: `https://localhost:7001/`
- client ID: `angular-web`
- redirect URI: `http://localhost:4200/auth/callback`
- response type: `code`
- scopes: `openid profile email billing.read` (request API-specific scopes as required)

The built-in ASP.NET Core Identity UI provides the login page at `/Identity/Account/Login`. The authorization endpoint challenges the Identity application cookie and resumes the authorization request after login.

Example Angular-side configuration using `oidc-client-ts` (install with `npm install oidc-client-ts`):

```typescript
import { UserManager, WebStorageStateStore } from "oidc-client-ts";

export const userManager = new UserManager({
  authority: "https://localhost:7001/",
  client_id: "angular-web",
  redirect_uri: "http://localhost:4200/auth/callback",
  response_type: "code",
  scope: "openid profile email billing.read payment.read",
  userStore: new WebStorageStateStore({ store: window.sessionStorage }),
  automaticSilentRenew: false
});

// Login button:
await userManager.signinRedirect();

// Callback route after IAM redirects back:
const user = await userManager.signinRedirectCallback();
const accessToken = user.access_token;
```

Use HTTPS redirect URIs outside local development. For API-specific audience isolation, request only the scopes needed for the target API; the token's `aud` is derived from the registered scope resources. If the frontend needs several independent API audiences, obtain separate API-specific access tokens rather than assuming one token is valid everywhere.

For production, serve the SPA over HTTPS, use exact redirect URIs, add MFA/email confirmation, and consider a BFF architecture if browser token storage is a concern. Never put a confidential client secret in Angular.

## 8. Service-to-service examples

### Billing -> Pricing

Billing requests a token using HTTP Basic client authentication:

```http
POST https://localhost:7001/connect/token
Authorization: Basic base64(billing-service:secret)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&scope=pricing.read
```

It caches the short-lived token and calls `GET https://localhost:7003/api/prices/customer/{id}`. Pricing validates issuer, signature, expiry, `aud=pricing-api`, and `scope=pricing.read`.

### Payment -> IAM

Payment obtains a token as `payment-service` with `scope=users.read`, then calls `GET https://localhost:7001/api/users/{id}`. IAM's user endpoint validates the JWT as a resource API with `aud=iam-api` and `users.read`.

## 9. Test the API calls

First obtain user access tokens through an OIDC client using the Authorization Code + PKCE flow. Then:

```bash
curl -H "Authorization: Bearer <user-token-with-billing.read>" \
  https://localhost:7002/api/billing/customer/customer-123/charge

curl -H "Authorization: Bearer <user-token-with-payment.read>" \
  https://localhost:7004/api/payments/customer/<user-id>/profile
```

The downstream service tokens are obtained by the APIs automatically. The sample Pricing endpoint returns a fixed demonstration amount; replace it with the Pricing domain query.

## 10. Production hardening required before go-live

This starter is an implementation baseline, not a security certification. Before production:

1. Use .NET 10 current servicing patches and current compatible package patches.
2. Configure trusted reverse proxies/forwarded headers and a canonical HTTPS issuer.
3. Use distinct RSA signing and encryption certificates/keys in Key Vault/HSM; rotate signing keys with overlap and verify JWKS propagation.
4. Store OAuth client secrets in a vault, rotate them, and avoid logging credentials or tokens.
5. Add MFA, email verification, account recovery, lockout telemetry, admin RBAC, and audited user/client administration.
6. Add explicit consent policy if third-party clients are introduced. The sample uses implicit consent only for the first-party Angular client.
7. Add refresh-token rotation/reuse protections and test revocation/session termination behavior.
8. Add rate limits, WAF, structured audit logs, metrics, distributed tracing, backups, disaster recovery, and security tests.
9. Use managed identity / workload identity for infrastructure and messaging permissions; OAuth client credentials here are for HTTP resource API calls.
10. Add integration tests for wrong issuer, wrong audience, expired token, missing scope, disabled user, invalid client secret, and token refresh.
11. Replace the sample user-profile response with a DTO that exposes only fields each caller is authorized to see.
12. Do not treat `userId` in a message or request body as proof of the user's identity. Authorize access to the referenced customer/user independently.

## Design choices

- All resource APIs use the normal `Bearer` scheme; no custom `JwtClientCredentials` scheme.
- User tokens and service tokens have distinct subjects and intended audiences.
- Each service has its own OAuth client identity and least-privilege scopes.
- JWT validation is local using discovery/JWKS; APIs do not call IAM for every request.
- Client credentials tokens are cached in-process with a single-flight lock. In multi-instance deployments each instance may obtain its own token; this is expected. Use a distributed cache only if your operational/security model requires it.
- The sample does not implement OAuth Token Exchange. Add delegation only if a downstream service must authorize the actual user, not merely trust the calling service.
